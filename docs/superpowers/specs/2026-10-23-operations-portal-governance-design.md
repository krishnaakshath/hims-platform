**Date:** 2026-10-23 · **Status:** approved under the owner's standing instruction · **Parent:** `docs/superpowers/specs/2026-10-23-hospital-completion-design.md` (sub-project 5) · **Findings:** `docs/superpowers/plans/2026-10-23-gap-closure-plan.md` sections C, D, F, G, H, I, J, K and UI list section 5.
**Plans:** `docs/superpowers/plans/2026-10-23-pharmacy-frontdesk.md` (WS5, WS6) and `docs/superpowers/plans/2026-10-23-forms-portal-governance.md` (WS7, WS8, WS9).

## 1. Intent

Close the daily-use gaps in pharmacy, front desk, forms, the patient portal and governance, then finish the UI list. Every change reuses the merged foundations: `trialsEnabled()`, the blob driver, the notification service (`sendNotification`, `notification_log`, per-patient channel preferences), the lab price gate, and the UPI payment path (`createUpiRequest`, `confirmUpiRequest`, `recordPayment`). Nothing here adds a dependency to `package.json`.

**Preconditions.** Foundations Tasks 8–9 (notification service, branch `feat/hc-s8`) must be merged into `feat/hospital-completion` before any task that calls `sendNotification`. Every such task says so. Implementers read `node_modules/next/dist/docs/` before touching routing, caching, `searchParams` or route handlers (AGENTS.md: this Next.js has breaking changes).

**Neighbouring sub-projects (coordinate, do not duplicate).** Read `docs/superpowers/specs/2026-10-23-doctor-workspace-billing-design.md` (WS1/WS2) and `docs/superpowers/specs/2026-10-23-inpatient-lab-design.md` (WS3/WS4) before starting.
- **WS1/WS2 own** (their decisions 7–9, 14): the multi-drug prescription builder (`prescriptions` header table, `medication_episodes.dose_pattern/route/food_timing/is_sos/quantity_prescribed/allergy_override_reason`, mandatory dose, `parseDosePattern`, `prescribedQuantity`, `allergyConflicts`), dispense pricing and automatic billing in the dispense transaction (`captureAutoChargeInTx`, `pharmacyLinePrice`, `medications.mrp_per_unit_paise`, `medication_dispenses.batch_no/expiry_month/unit_mrp_paise/no_charge_reason`), the dispense dialog's quantity prefill, price, allergy banner and success toast, removal of HCPCS `J3490`, `encounter_notes.encounter_id`, and the `signable_type` value `encounter_note`. Findings A5, B2, B3 and the dispense half of D1 close there. This sub-project does **not** rebuild any of it.
- **WS5 owns** stock by batch, FEFO, GRN, expiry alerts, reorder and write-off, and makes the WS2 dispense draw from a real batch: the batch chosen (FEFO or picked) fills WS2's `batch_no`, `expiry_month` and `unit_mrp_paise` snapshot. WS5 Task 5 therefore starts only after WS2's dispense change has merged.
- **WS3 owns** bed-board cards and actions (days stayed, bed tariff, Transfer / Discharge / MAR / Charges) and the discharge dialog. WS9 does not touch `BedBoard.tsx` or `DischargeAdmissionModal.tsx` beyond the "Wound VAC" placeholder.
- **WS7 owns** note re-authentication (WS1 lists it out of scope); it reuses WS1's `encounter_note` enum value when present (`ADD VALUE IF NOT EXISTS`).
- **Shared UI primitive:** `ToastProvider` / `useToast` / `EmptyState` (D22) are built once, by Plan A Task 1. If WS1/WS2 land first with their own toast, Plan A Task 1 adopts theirs and only adds `EmptyState`; there must be one toast component in the tree.

## 2. Decisions (where the gap analysis is silent)

| # | Topic | Ruling | Reason |
|---|---|---|---|
| D1 | Stock model | New `medication_batches` (batch, expiry, MRP, purchase rate, quantity). `medication_inventory.quantity_on_hand` stays as the per-drug total, updated in the same transaction as batch changes, so every current reader keeps working. A migration backfills one "Opening stock" batch per drug with no expiry. | Smallest change that adds batches without rewriting the dashboard, KPIs and tests that read the total. |
| D2 | Dispense allocation | FEFO by default (earliest expiry first; no-expiry batches last); the pharmacist may pick a batch instead. Expired and written-off batches are never dispensed. **One dispense row = one batch**: when the FEFO batch is short, the route writes one dispense per batch in the same transaction, so each WS2 charge line carries its own batch and expiry. `medication_dispenses.batch_id` links the row to its batch. Batch MRP (`medication_batches.mrp_per_unit_paise`) is the MRP snapshot for that dispense; `medications.mrp_per_unit_paise` (WS2) remains the fallback for legacy stock. | Standard pharmacy practice; batch on the bill; no silent expiry. |
| D3 | Allergy warning | Owned by WS1/WS2 (`allergyConflicts`, `allergyAcknowledged`). WS5 does not add a second matcher. | One rule, one place. |
| D4 | Prescription shape | Owned by WS1 (`prescriptions` header + `medication_episodes` dose pattern). WS5 reads `quantity_prescribed` only through WS2's dialog. | Same. |
| D5 | Slot model | Weekly template per doctor (`provider_schedules`: weekday, start, end; several sessions per day allowed), slot length per doctor (5–60 min, default 15), leave days (`provider_leave`). Slots are computed on read, never stored. Booking still writes `appointments` through the existing conflict lock. A time outside working hours is allowed only after an explicit "outside working hours" confirmation. | No slot table to keep in sync; works with the existing overlap guard. |
| D6 | Doctors on public/portal booking and check-in | `providers.portal_bookable` (default true; migration sets false for doctors in non-`clinical` departments). Check-in lists only doctors in `clinical` departments, filtered by the chosen department. | Removes the pathologist from OPD and portal lists without hard-coding names. |
| D7 | Handover OTP | 6-digit code, scrypt-hashed, valid 15 min, 5 attempts, sent with `sendNotification` template `home_collection_handover_otp`. Collect requires the code, or a waiver reason (patient has no phone, or SMS is log-only). | Proof of handover without blocking collectors where SMS is not configured. |
| D8 | Payment at the door | The collector uses the one payment path: cash → `recordPayment` (mode `cash`), UPI → `createUpiRequest` QR + `confirmUpiRequest` with UTR, only for a visit assigned to them, only on its visit date. | One ledger (foundations 4.6). |
| D9 | Form model | Template questions gain types `number`, `phone`, `file`, `signature`, `section`, an optional `visibleIf { questionId, equals }`, and `i18n { hi?: { label, options? }, kn?: {...} }`. Answers stay keyed by question id; select answers store the English option value. | Language-neutral answers; reports and scoring keep working. |
| D10 | Translations | Human-entered per-string translations; English is required; Hindi and Kannada fall back to English string by string. No machine translation. Seeded Hindi/Kannada texts are marked draft and consent documents stay `legal_review_status = 'draft'` until reviewed. | Consent wording is legal text; machine output is not acceptable. |
| D11 | Empty draft | "Create New Form" opens `/forms/new` (client state only); the first edit creates the template and replaces the URL with `/forms/<id>`. | No more stray "Untitled Form" rows. |
| D12 | Note signing | Signing a clinical note needs the typed own name, the attestation tick and re-authentication: the account password, or a current TOTP code for accounts without a password (Google sign-in). The env-configured admin re-authenticates against `ADMIN_PASSWORD_HASH`. A `signatures` row (`signable_type = 'encounter_note'`) is written in the same transaction. Rate-limited per user. | Reuses the discharge pattern and adds a real second check. |
| D13 | Portal 2FA | Staff MFA stays required (`DISABLE_STAFF_MFA` is demo-only). Patient MFA is **offered, not required**: the portal shows a persistent nudge until enabled; OTP sign-in remains. README lines claiming mandatory patient MFA are corrected. | Many patients have no authenticator app; the README must not overstate. |
| D14 | Portal pay now | The portal creates a UPI request (QR) for a finalised invoice's outstanding amount. A patient may report a UTR; that never posts to the ledger. The cashier confirms it from the Cash Desk's pending UPI list (existing confirm route). | A patient-typed UTR is unverified; only staff post receipts. |
| D15 | Portal self-service | Policy and ABHA uploads land in `portal_submissions` (pending). Front desk approves (writes the real policy with `createPolicy`, or records the ABHA as "recorded, not verified") or rejects with a reason. | Staff stay the gatekeepers of master data. |
| D16 | Broadcasts | Real delivery through `sendNotification` with template `broadcast_notice`; opted-out patients and patients with no usable phone are skipped and counted. The sender confirms by typing the recipient count. History stores filters and sent/skipped/failed counts; per-recipient rows live in `notification_log`. Trial filters appear only when `trialsEnabled()`. | Fixes K11 without a second delivery path. |
| D17 | Patient delete | "Delete" becomes **archive**: `patients.archived_at`, `archived_by_name`, `archive_reason`. Admin only, typed-UHID confirmation, reason ≥ 10 characters, audit row. Archived charts are hidden from lists, search, pickers, broadcasts, queue and portal sign-in; admin can view (banner) and restore. The hard-delete function remains internal, reachable only from DPDP erasure when no retained records exist. | Medical and tax records must be kept; mistakes must be reversible. |
| D18 | DPDP | Minimal register: `data_principal_requests` (access, correction, erasure, grievance), due 30 days from receipt, fulfilment checklist, export bundle (existing `buildFullBundle` FHIR JSON + manifest) stored with the blob driver and downloaded through an audited route. Erasure archives the chart and scrubs contact fields when retention applies; it never deletes financial or medico-legal records. Retention periods are a code constant shown on the page, marked "default, pending legal review". | Meets the H3 ask without inventing legal advice. |
| D19 | Audit log | Keyset pagination (50 per page), filters (user, role, patient UHID/chart id, action text, date range IST), CSV export capped at 50,000 rows, cells starting `= + - @` prefixed with `'`, export itself audited. | F5. |
| D20 | Visit mode | `appointments.visit_mode` (`in_person` default, `video`). Only video appointments offer telemedicine; a row with an existing session shows "Rejoin (session active)". | I14, K9. |
| D21 | Queue display | Shows "Now serving" (latest `ready` tokens) with doctor name and room, never patient names. Labels in English, Hindi, Kannada from a static dictionary chosen by `?lang=`. Settings card generates a random 6-digit PIN and links to a preview. | C8, I15, UI 12. |
| D22 | Toasts and empty states | In-house `ToastProvider`/`useToast` and `EmptyState` in `src/components/ui/`; no new package. Toasts carry an optional next-step link. | UI 3, consistent empty states. |

## 5. Error handling

- Refusals are typed results mapped 1:1 to HTTP: 400 bad input, 403 role or ownership, 404 missing, 409 state conflict (stock, expired batch, allergy, OTP, not yet visit day, duplicate UTR), 422 business rule, 429 rate limit, 503 service not configured (`serviceUnavailableBody`).
- No secret, OTP, password, UTR, provider body, blob URL or file path is logged or returned; logs carry error class names only. Audit details carry ids and counts, never names, phones or answers.
- Money is integer paise; dates are IST business dates (`todayIsoIn`, `istDayBounds`); users see UHID, never chart ids (chart id only as a secondary hint where search already allows it).

## 6. Testing

- Unit tests for every pure module above.
- DB-backed route tests on the isolated `hims_test` database only (`source $SCRATCH/testenv.sh`); never `.env.local`, the demo DB or a cloud DB.
- Component tests for dialogs and pages (GRN, batch picker, slot picker, check-in, queue display, form builder, intake renderer, audit log, archive dialog, broadcast wizard).
- Both RBAC harnesses get a row for every new route and page.
- A Docker walkthrough at the end of each plan covers each finding it closes, with `ENABLE_TRIALS` unset and again with `true`.

## 7. Out of scope

Drug-interaction database; supplier master and purchase orders beyond GRN receipt; real telemedicine chat, screen share and chart panel; machine translation; DPDP consent manager integration; breach-notification tooling; bed-board cards and actions (WS3); prescription builder, allergy matcher, dispense pricing, GST and dispense dialog prefill/toast (WS1/WS2).
